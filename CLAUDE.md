## Project status

Fresh-from-template macOS SwiftUI app generated by Xcode on 2026-05-19. Nothing app-specific has been built yet — the four Swift files and the Core Data model are still the default "Item with a timestamp" scaffolding. There is no README, no tests, no CI, no package manager, no lint config.

When the user starts building something real here, expect to replace, not extend, the template files (`ContentView.swift`, `Persistence.swift`, the `Item` Core Data entity).

## Build & run

This is an Xcode project (`lexi.xcodeproj`), not a Swift Package — there is no `Package.swift` and no SwiftPM dependencies. Build from the command line with:

```sh
xcodebuild -project lexi.xcodeproj -scheme lexi -configuration Debug build
```

To launch the app, open `lexi.xcodeproj` in Xcode and Run (⌘R). Target is **macOS 26.4**, Swift 5.0, `SDKROOT=macosx`. There is no iOS / iPadOS target.

There is no test target yet, so `xcodebuild test` will fail until one is added.

## Architecture

Standard Xcode "App + Core Data" template:

- [lexiApp.swift](lexi/lexiApp.swift) — `@main` entry, injects the Core Data view context into the SwiftUI environment.
- [Persistence.swift](lexi/Persistence.swift) — `PersistenceController` wraps an `NSPersistentContainer` named `"lexi"`. Exposes `.shared` (on-disk) and `.preview` (in-memory, pre-seeded with 10 items, for SwiftUI previews).
- [ContentView.swift](lexi/ContentView.swift) — `NavigationView` + `@FetchRequest` list of `Item`s with add / delete toolbar buttons.
- [lexi.xcdatamodeld](lexi/lexi.xcdatamodeld) — single `Item` entity, one `timestamp: Date?` attribute, `codeGenerationType="class"` so the `Item` NSManagedObject subclass is generated by Xcode at build time (no source file exists for it).

The container name (`"lexi"` in `Persistence.swift`) must match the `.xcdatamodeld` filename, otherwise the store fails to load.

The template's error paths all `fatalError()`. That's fine while the file is still untouched scaffolding; once real code lands those should be replaced with proper handling — don't carry the `fatalError` pattern into new code.
